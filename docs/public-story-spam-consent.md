# Story submission spam-protection consent

This follow-up applies Wave 2's global third-party permission rule to the existing public story form. It reuses the exact `src/lib/reader-consent.js` module from B1 PR #46. The B1 privacy dialog supplies the shared revocation controls; no owner analytics ID or production decision is implied.

With endpoint and site key configured, the form still makes no Cloudflare request until the reader explicitly presses **Allow spam protection**, or has already granted the shared forms permission. The adjacent notice names Cloudflare and tells readers where to withdraw permission. The button saves only the existing versioned boolean service choices; no form content, personal data or challenge token enters browser storage. Revoking permission removes the widget and clears its token. Granting permission from the form immediately synchronises the privacy dialog checkbox through the shared consent module; revocation synchronises it back. Navigation unsubscribes listeners, disposes the widget, clears fields and aborts an outstanding form request.

Story field IDs, required phone, JSON payload, `submit-story` action and real submission endpoint behavior are unchanged. The old fallback contact form also inherits this gate before the separate C5 reader integration replaces it. Unconfigured forms remain disabled and never load a widget.

The legacy form contract browser suite explicitly opts into spam protection before completing its STUB Cloudflare widget. Its API responses and Cloudflare transport are STUBS, not end-to-end proof. The additional desktop/Pixel 7 check verifies there is no script/request before permission, one after permission and no usable token after revocation. Storage checks now permit only the explicit boolean consent record, while still rejecting stored form data.

The real Payload/PostgreSQL public CMS suite's existing helper also explicitly grants permission. That lane still uses a STUB Cloudflare/Siteverify transport and reports it separately; no claim of real external verification is added. The PR includes no CMS/newsroom source changes, production scripts, merge or deploy. Feature PRs contain no generated Pages asset or index hash changes; one dedicated rebuild follows the integrated source changes.
