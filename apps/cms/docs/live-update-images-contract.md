# Live update photos: contract addition and rendering guidance for the public site

Status: implemented in the CMS (contract v1.4, migration `20261014_203617_live_update_image`). Additive: nothing that
exists today changes. This file is the text the public-site team can paste into `docs/public-live-coverage.md`
(contract section); that file is not edited from the CMS side.

## 1. Contract addition: `GET /api/live-events/:slug/updates`

Every item in `docs` gains one key, `image`:

```json
{
  "id": 41,
  "sequence": 7,
  "body": "Delegates vote on the amendment.",
  "occurredAt": "2026-10-13T10:15:00.000Z",
  "approvedAt": "2026-10-13T10:16:02.000Z",
  "image": {
    "url": "https://cms.example.org/api/media/file/vote.jpg",
    "alt": "Delegates raising voting cards in the synod hall",
    "width": 1600,
    "height": 900,
    "mimeType": "image/jpeg"
  }
}
```

An update without a photo has `"image": null`. The key is always present.

| Field | Type | Guarantees |
| --- | --- | --- |
| `image` | object or `null` | `null` when the update has no photo (or the attached file is not a usable image). |
| `image.url` | string | **The ~800 px wide `card` variant** of the upload (not the original, which can be up to 10 MB), or the original upload when no such variant exists. Same form as `featuredImage.url` of articles: absolute `${CMS_PUBLIC_URL}/api/media/file/<name>` in production, root-relative `/api/media/file/<name>` only in a local CMS without `CMS_PUBLIC_URL`. The path always starts with `/api/media/file/`. Run it through the same check as article media (`normalizePublicMedia` / `mediaUrl` in `src/lib/published-articles.js`: http(s) only, same origin as the configured CMS, path prefix `/api/media/file/`). |
| `image.alt` | string | Never empty (the CMS refuses to attach, or to approve, an image without alt text). Plain text, up to 300 characters. |
| `image.width`, `image.height` | positive integer or `null` | Intrinsic pixel size of the file at `url` (for the variant: 800 and the proportional height). `null` only if the CMS does not know them. |
| `image.mimeType` | string | One of `image/jpeg`, `image/png`, `image/webp`: the type of the file at `url`. |

**Which file is served (contract v1.5).** Readers get the `card` size generated by Payload (800 px wide, same format as the
upload). Payload does not enlarge, so an upload narrower than 800 px has no variant and its original is served; the same holds for
media uploaded before the size existed. The fields always describe the file at `url`; never assume 800 px or compute a ratio from
anything else. The five keys and the `/api/media/file/` path guarantee are unchanged.

Exactly these five keys are returned. No filename, caption, credit, other resized variants (the `url` is just one of them), uploader or other staff field is
exposed. The image of a pending or rejected update is never **in the feed** (only approved updates are), and an update that
is rejected after approval disappears from the feed together with its image, as before. This is a statement about the feed
only, see section 3 for what is and is not protected elsewhere.

Unchanged: ordering by publication `sequence`, `since` / `nextSince`, `limit`, status codes, `Cache-Control: public, max-age=10`.
A client that does not look at `image` keeps working. A client or test that asserts the exact key set of a feed item must now expect
`['approvedAt', 'body', 'id', 'image', 'occurredAt', 'sequence']` (the three existing exact-key assertions in the repository
were updated accordingly: `apps/cms/tests/integration/live.test.ts`, `apps/cms/e2e/cross-app/07-live-coverage.spec.ts`,
`cms-integration-tests/public-live.spec.js`).

### Edits of an already published update (new behaviour, public client must replace by `id`)

An editor (or a trusted publisher, for their own update) can change the `body` or the `image` of an update that is already
approved. Each such change gives the update a **new, higher `sequence`** (the same mechanism as an approval), so every poller,
whatever its `since`, receives it again. What the client receives:

```json
{ "id": 41, "sequence": 12, "body": "<current text>", "occurredAt": "…unchanged…", "approvedAt": "…unchanged…", "image": { … } | null }
```

- the **same `id`** as before, a `sequence` greater than any it has seen, the **current** `body` and the **current** `image`
  (`null` if the photo was removed);
- `occurredAt` and `approvedAt` do not change, so keep ordering the timeline by `sequence` (publication order) and show the
  original times;
- a PATCH that changes neither `body` nor `image` does not produce a new delivery.

**The current public client does not handle this and must be changed** (read-only review of `src/live/public-live-page.js` and
`src/lib/public-live.js`):

1. `loadUpdates()` skips every update whose `id` (or `sequence`) it has already seen (`if(ids.has(update.id)||sequences.has(update.sequence))continue;`),
   so the corrected item is dropped and the old text stays on screen until the page is reloaded (a reload then shows it once,
   at its new position).
2. `normalizeLiveUpdate` copies only `id, sequence, body, occurredAt, approvedAt`, so `image` is discarded.
3. The consistency check in `fetchLiveUpdates` already accepts the new sequence (it only requires `sequence > since` and
   `nextSince` = max sequence), so the cursor advances correctly.

Required behaviour: key the timeline by `id`. If the `id` is already rendered, **replace** that `<li>` (text, figure, and its
`data-sequence`) and move it to the position implied by the new `sequence`; remove the figure when `image` is `null`. Track
`sequences` only to detect true duplicates of the same `(id, sequence)` pair, not to ignore a known `id`. Announce a replaced
item as "update corrected" rather than as a new update.

Known gaps (not covered by this mechanism):
- If a media document is **deleted** while an approved update uses it (`ON DELETE SET NULL`), no CMS hook runs. A fresh
  load shows the update without an image, but pollers already past it are not re-sent the update and keep showing the photo until
  they reload. No `live-update.image` audit entry is written for that case (only the media delete itself is audited as
  `delete` on `media`). Editors should replace or remove the image on the update first, then delete the media.
- Rejecting an update still removes it from the feed only for new reads; clients must drop rejected items on reload (unchanged).

## 2. Rendering guidance

- Show the photo **above** the update text, inside the update item (a `<figure>` with the `<img>`, then the text).
- Build the element with DOM APIs (`document.createElement('img')`, set `src`, `alt`, `width`, `height` as properties or
  attributes). **Never put `image.*` into `innerHTML`**, and never render any of it as HTML. `alt` is text; set it via
  the `alt` attribute or `textContent`, never interpolated into markup.
- `alt={image.alt}` always. Do not fall back to an empty alt (the field is guaranteed non-empty), and do not repeat the
  update body as alt.
- `loading="lazy"` and `decoding="async"`. A timeline can hold up to 100 items per poll, so only the images near the
  viewport should load. (The first image above the fold may stay eager if the page wants it; lazy is the safe default.)
- Always set `width` and `height` from `image.width` / `image.height` when present, and let CSS scale the image
  (`max-width: 100%; height: auto;`). The browser then reserves the right space and live updates do not shift the page.
  When `width`/`height` are `null`, give the figure a reasonable `aspect-ratio` placeholder (for example `16 / 9`) instead.
- Remove the `<figure>` if the image fails to load (`error` event), as `bindCMSImages` already does for article images,
  so the update text remains and no broken icon is shown.
- Do not wrap the image in a link to the media URL, and do not use `image.url` as a CSS `background-image` string without
  the same URL validation.
- New items arrive via polling: when you append or update an item, create the figure with the same code path as the
  initial render, so lazy loading and the error handler apply to polled items as well.
- Images are not keyed by URL: if the same `id` arrives again with a different (or `null`) `image`, replace or remove the
  figure to match.

## 3. What is and is not protected (media read access)

Since API contract v1.6 the `media` collection is **not** publicly readable any more. Anonymous callers can read a media
document, list it, and download its file and size variants (`GET /api/media`, `/api/media/:id`, `/api/media/file/<name>`) only when
it is the featured image or a body image of a **published** article, or the photo of an **approved** live update on a `live`/`ended`
event. Everything else (drafts, in-review, scheduled or archived articles, pending or rejected live photos, unreferenced uploads)
answers 403 (file) or 404 (document) to anonymous callers; staff read everything. A file stops being public again when its article is
unpublished or its update un-approved, so do not put a long-lived shared cache in front of `/api/media/file/*` without revalidation.
Details: `api-contracts.md` section 3 (Media) and 6.3, `docs/security.md`.

## 4. Staff side (for the newsroom app)

`POST /api/live-updates { event, body, image?: <media id> }` and `PATCH /api/live-updates/:id { image: <media id> | null }`.
Upload the file first (`POST /api/media`, multipart, `alt` required) and send the returned `id`. Refusals are `400` with
one of: *The attached image does not exist or is not available to you.*, *The attached image must be a JPEG, PNG or WebP
image.*, *The attached image needs alt text. Add a description to the image first.* The edit rules are those of `body`
(reporters: own `pending` updates only; editors in scope: any time; trusted publishers: their own updates). An image change
is audited as `live-update.image` and, for an approved update, re-stamps its `sequence` (see above). Non-editors cannot edit or
replace (multipart) the media of an approved update (`403`).
Full detail: `apps/cms/docs/api-contracts.md` §4.3, §6.2 and §9 (v1.4).
